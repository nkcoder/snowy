# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What is this

Snowy is a desktop PostgreSQL GUI client built with [Wails v3](https://v3.wails.io/) — Go backend + React/TypeScript frontend bundled into a native app. The Go code exposes methods to the frontend via Wails bindings; the frontend calls them through auto-generated wrappers in `frontend/bindings/`.

## Commands

Day-to-day: `just start` (demo DB + app in the background), `just logs`, `just stop`, `just test`. The raw commands behind them:

### Development
```bash
wails3 dev -config ./build/config.yml   # hot-reload dev mode (runs both Go and Vite)
```

### Build
```bash
just package   # production bin/snowy.app with embedded frontend
cd frontend && npm run build    # TypeScript check + Vite build only
```

### Frontend tests
```bash
cd frontend && npm run test              # run vitest once
cd frontend && npm run test:watch        # watch mode
cd frontend && npx vitest run src/components/Sidebar.test.tsx  # single file
```

### Backend tests
```bash
go test .                                                                       # unit tests (no DB needed)
TEST_DB_URL=postgres://myuser:mypassword@localhost:5432/mydatabase go test .    # + integration tests
```

### E2E tests (Playwright)
```bash
npx playwright test                                              # all specs
npx playwright test e2e/sidebar.spec.ts                         # single spec
# Playwright auto-starts the Vite dev server on :5173 if not already running
```

### Demo database
```bash
docker compose -f docker/docker-compose-postgresql.yml up -d
# credentials: postgres://myuser:mypassword@localhost:5432/mydatabase
```

## Architecture

### Backend (Go)
- `main.go` — Wails bootstrap; embeds `frontend/dist` at compile time
- `app.go` — `App` struct with all exported methods bound to the frontend; thin wrappers that delegate to services
- `config.go` — `ConfigManager` reads/writes `~/.snowy/config.json` via `sync.RWMutex`; holds `Project` and `Datasource` structs. Passwords are **not** written to the config file — they live in the macOS Keychain (see `keychain.go` / ADR-0003); the on-disk `datasourceRecord` has no password field
- `keychain.go` — `KeyringStore` interface over the macOS Keychain (service `app.snowy.connections`), keyed by datasource ID; mocked in tests
- `db_service.go` — `DbService` keeps one `pgxpool.Pool` per datasource (lazy, cached in a `sync.Map`) with a stale-pool retry in `acquire()` (see ADR-0002); schema/table/column/key/FK/index/check introspection and query execution; completion cache via `sync.Map`
- `query_service.go` — saves/loads/lists/renames `.sql` files under `~/.snowy/queries/<dsId>/`
- `history_service.go` — appends query history to `~/.snowy/history/<dsId>.jsonl`, newest-first on read

### Frontend (React + TypeScript + Tailwind)
- `frontend/src/App.tsx` — root component holding all app state; two views: `connections` (ConnectionManager) and `workspace`
- `frontend/src/components/Sidebar.tsx` — lazy-loading tree: datasources → schemas → tables → sub-folders (columns · keys · foreign keys · indexes · checks). Each table node uses `SubFolder<T> = { open, items, loaded }`. Columns auto-open on first table expand; others load lazily on click and cache — no re-fetch on reopen.
- `frontend/src/components/QueryEditor.tsx` — CodeMirror SQL editor with DB-aware autocomplete
- `frontend/src/components/ResultsPanel.tsx` / `ResultsTable.tsx` — tabular results with pinnable tabs and CSV export
- `frontend/src/components/ConnectionManager.tsx` — datasource CRUD + test-connection form
- `frontend/src/components/TabBar.tsx` — query console tabs with dirty-state tracking
- `frontend/src/components/HistoryDrawer.tsx` — slide-out query history panel
- `frontend/src/lib/tokens.ts` — all colors/fonts as `T.*` → `var(--t-*)` CSS custom properties; never use hardcoded hex values in components
- `frontend/src/types.ts` — shared `Project` and `Datasource` interfaces mirroring Go structs
- `frontend/bindings/snowy/` — generated Wails bindings (`app.ts`, `models.ts`); committed, regenerated by `just dev`/`just package` or `wails3 generate bindings -ts -clean=true`; never edit by hand
- `frontend/src/backend/` — the only place components import Wails from: `app.ts` re-exports the bindings, `models.ts` the model classes, `events.ts` wraps the runtime `snowy:notification` listener

### Wails binding contract
- `App` is registered as a Wails service; any exported method is callable from the frontend through the generated bindings, imported via `src/backend/app`
- After adding or changing a Go method: run `wails3 generate bindings -ts -clean=true` and commit `frontend/bindings/`
- Lifecycle is `ServiceStartup(ctx, options)`; native dialogs and events go through `application.Get()`
- Go nil slices serialize as JSON `null` — always use `make([]T, 0)` instead of `var items []T` in DB methods to ensure the frontend receives `[]`, not `null`

### Testing approach
- **Go unit tests**: file-system operations use `t.TempDir()` + `t.Setenv("HOME", tmp)` — no DB required; integration tests in `db_service_test.go` skip unless `TEST_DB_URL` is set
- **Frontend unit tests**: vitest + jsdom; backend mocked via `frontend/src/test/mocks/wailsjs.ts`, mapped by alias in `vitest.config.ts`, and `vi.mock('../backend/...')` in tests — add new Go methods to the mock when extending the API
- **E2E tests**: Playwright against the Vite dev server; Playwright starts Vite with `E2E_MOCK=1`, which swaps `src/backend/app.ts` for `e2e/backend-shim.ts`; `e2e/mock-bridge.ts` installs the `window.go.main.App` mock it reads via `page.addInitScript` — add new Go methods to both (the shim's export list and the bridge); no real DB needed for e2e

## Development workflow

Work is tracked as GitHub issues (labelled `bug` / `enhancement` / etc.); each issue is an independent, runnable increment. When completing an issue: run all test suites, verify with `wails3 dev` against the demo DB, raise a PR that closes the issue.

Create a new branch for each issue (bug, feature, enhancement, refactor etc.).
Use /tdd for development.
Use /playwright-cli for testing.
Use caveman mode if possible.

## Key constraints
- One `pgxpool.Pool` per datasource, created lazily and cached; `acquire()` retries once on a stale pool after long idle (see `docs/adr/0002-connection-pooling.md`)
- Config is written atomically (file first, then Keychain); passwords are stored in the macOS Keychain, never in `~/.snowy/config.json` (see `docs/adr/0003-keychain-password-storage.md`)
- `frontend/dist` must exist before building (embed fails otherwise); `just package` builds it; a manual `go build` does not
- **Tailwind v4** (`@tailwindcss/postcss`): `frontend/src/style.css` must start with `@import "tailwindcss";` — the v3 `@tailwind base/components/utilities` directives don't load the default theme in v4, so `--spacing` stays undefined and every spacing/typography utility (`px-*`, `pl-*`, `gap-*`, `w-1.5`, `text-xs`, `h-[22px]`, …) silently compiles to nothing while static ones (`flex`, `shrink-0`) still work. `tailwind.config.js` is not auto-loaded in v4 (content is auto-detected); reference it with `@config` if ever needed. If a spacing class has no visible effect, grep the built CSS in `frontend/dist/assets/*.css` for the rule before assuming the class name is wrong.
